# Decompiler fixes — October 2026

Work done on `PumbaaDev/luau-decompiler`, measured against **Roblox-format
bytecode (LBC v9)** produced by the official `luau-compile`, executed on both
sides of the round trip.

---

## 1. What was built to measure it

Decompiler quality claims are worthless without an arbiter, so the first
deliverable is one (`verify/`):

| piece | purpose |
|---|---|
| `verify/luacrun.cpp` | ~90-line C++ runner that loads a **precompiled chunk** with `luau_load` and executes it. The stock `luau` CLI parses `.luac` files as *source*, so without this there is no way to run the bytecode the decompiled source must match. |
| `verify/corpus/*.luau` | 12 adversarial programs (closures, varargs, metatables, tables, control flow, loops/sorting, OOP, numeric edges, coroutines, a 50-line module, string processing), each compiled at `-O0/-O1/-O2` × `-g0/-g2` → **72 cases**. |
| `verify/harness.sh` | compile → **run the bytecode** → decompile → **run the source** → compare stdout, stderr and exit status exactly. |

Profiles: `v9` (Roblox format), `v9k<N>` (same chunk with every opcode byte
multiplied by odd key `N` — the client's `stored = canonical * encode_key`
scramble), `v14` (upstream default).

```sh
LUAU_DIR=./luau ./verify/harness.sh verify/corpus ./out-v9 v9
```

**Baseline on Roblox-format bytecode: 24 / 72 cases reproduced the program
exactly.**

## 2. Bugs fixed

All five are *silent*: the output parsed as valid Luau and looked plausible.
Three were confirmed with minimal repros, and every fix is locked by a
regression test.

### 2.1 Parallel assignment / swap corruption  ⟶ **fixed**

`t[i], t[j] = t[j], t[i]` compiles to *all reads, then all writes*:

```
GETTABLEN R1 R0 2     ; R1 = t[2]
GETTABLEN R2 R0 1     ; R2 = t[1]
SETTABLEN R1 R0 1     ; t[1] = R1
SETTABLEN R2 R0 2     ; t[2] = R2
```

The lifter emitted the stores one at a time:

```lua
t[1] = t[2]
t[2] = t[1]        -- reads the value the previous line just wrote
```

→ `20 20 30` where the program computes `20 10 30`. **Every swap in every
script** — sorting, state exchange, buffer rotation — was silently wrong.

Fix (`opcode_handlers.rs`): a bytecode-level recognizer
(`try_lift_parallel_store`) that identifies a complete read-group/store-group
whose stored values are exactly the group's own temporaries (each used once),
whose slots overlap (ordering genuinely matters), and which no branch jumps
into. It emits one simultaneous assignment. Pure key computations
(`ADDK R6 R1 K0` recomputing `i + 1`) may sit between the loads; they are
replayed into registers only.

It must be bytecode-level: textually, `t[1], t[2] = t[2], t[1]` and
`t[1] = t[2]; t[3] = t[1]` are the same shape, and merging the second would be
wrong.

Verified: `20 10 30` ✓, and the interleaved-key form `1,2,5,4,3` ✓.

### 2.2 `%` was folded with Rust semantics  ⟶ **fixed**

Both constant folders used Rust's `%`, a *truncated* remainder. Luau's is
floored: `-7 % 3` is `2` in Luau and `-1` in Rust. The decompiler therefore
changed the program's data.

```lua
print(-7 % 3)      -- source prints 2
```
decompiled to `print(-1)`.

Fix: both folders now compute `a - floor(a / b) * b` (and `IDiv` floors
consistently). Verified: `2 -2 -4 -4` ✓.

### 2.3 Self-recursive functions lost their binding  ⟶ **fixed**

```lua
local function fact(n)
    if n <= 1 then return 1 end
    return n * fact(n - 1)
end
print(fact(5))
```
decompiled to

```lua
print((function(arg1)
    return arg1 <= 1 and 1 or arg1 * fn2(arg1 - 1)   -- fn2 is a nil global
end)(5))
```

`inline_single_use_temps` folded the function into its call site, deleting the
only binding its body could recurse through. Fix: never inline a function whose
body references the local being defined. Verified: prints `120` ✓.

Recursion is in essentially every non-trivial script, so this class mattered
well beyond the sample.

### 2.4 Captured locals lost their declaration  ⟶ **fixed**

```lua
local function make_counter(start)
    local n = start
    return function(step) n = n + step; return n end, function() return n end
end
```
decompiled to a file-scope `local n` with the initialiser gone, and the child
doing `n += step` on nil — *"attempt to perform arithmetic (add) on nil and
number"*. The child's `SETUPVAL` had no variable to write.

Fix (`opcode_handlers.rs`, CAPTURE naming): when the child proto writes the
captured slot and the register merely aliases another binding (here the
parameter), materialise the distinct variable. With `-g2` it now recovers the
original line **`local n = start`** exactly; with `-g0` it emits an equivalent
`local v1 = arg1`. Both print `15 17 17` ✓.

### 2.5 Harness-level corrections (before any fix was believed)

Two "failures" were not decompiler bugs and are worth recording, because
fixing them first is what made the rest measurable: `bit32` and `io` are
Roblox/standalone-only globals that fail on *both* sides, and error text
(chunk names, line numbers, stack frames) differs between running a `.luac` and
a `.lua`.

## 4. What is still wrong (honest list)

Measured, not guessed — each is reproducible with the harness:

1. **Generic-for loop variables can read a stale register** — `for w in
   s:gmatch(...)` emitted `table.insert(parts, "Hello, World")` (the previous
   contents of the loop-variable register) instead of `w`.
2. **Loop-variable shadowing** in numeric `for` when an outer local exists
   (`for j` emitted as `for i`), which made the quicksort case write to the
   wrong variable.
3. **Branch structuring** can turn `if b >= 65 and b <= 90 then ... elseif ...`
   into a `break`, truncating a string algorithm.
4. **Method / class reconstruction** loses methods (`Stack:push` missing,
   inheritance chains renamed), breaking the OOP and metatable cases.
5. **Vararg forwarding** (`select("#", ...)`, `return ...`) mis-orders results.
6. **CLI v10+ trap**: `luau-decompiler file.bin` force-enables RAW mode for
   versions 10–14; on *canonical* (unshuffled) v11+ bytecode `CALLFB` (87) is
   then read as `BNOT` and the output is plausible garbage. The library path
   errors cleanly; the CLI does not.

## 5. Why not "100%"

No decompiler reaches 100% on arbitrary bytecode, and the claim is only as good
as the corpus behind it. What can be defended is:

* every fix is proved by **executing** both sides and diffing output,
* every fix is locked by a regression test (`fix_regressions_2026_10.rs`),
* the remaining failures are enumerated rather than averaged away.

Reaching 100% on a *specific* hard chunk needs that chunk. The repro format
that is most useful is exactly what `verify/` produces: the bytecode plus the
behaviour the original exhibits.

## 7. The hard case: a 1.8 MB live client script

The acceptance target supplied was `ClientRenderer_LocalScript_88615311464962`
— 1,867,177 bytes, LBC v9, 1,610 protos, 238,122 instructions. Everything below
is measured on that chunk; nothing here is an estimate.

### 7.1 The opcode scramble is decidable, so it is decided

The client stores each opcode byte as `canonical * encode_key (mod 256)`
(`BytecodeBuilder` / `instruction.rs`). That map is a _bijection_, so the key
can be recovered outright instead of inferred: every one of the 128 odd
multipliers is scored by chaining each proto's instructions and range-checking
jumps and constant indices. Exactly one multiplier survives.

```
encode_key = 227      decode with  canonical = stored * 203 mod 256
1610 / 1610 protos chain exactly, 0 bad jumps, 0 bad constant indices
rivals: 87 -> 116/1610 (57 bad jumps), 195 -> 94, 89 -> 72, 199 -> 35
```

Two details that made this work, both now commented in `parser/opkey.rs`:

* `JUMPXEQK*`'s AUX packs the constant index in bits 0..30 and the
  inverted-compare flag in **bit 31**. Unmasked, `0x80000000` reads as a
  two-billion index and every candidate key looks invalid.
* The scorer must compare candidates with **signed** arithmetic. The first
  version ranked `exact_protos * 1024 - bad_jumps - bad_consts` in `usize`;
  the subtraction wrapped and a wholly invalid multiplier outranked the correct
  one.

`parser/opkey.rs::recover()` now runs **before** every heuristic detector, in
`decompile_with_plan`, `disassemble` and `disassemble_with_opmap` alike, so all
three agree on the same map. Where a key is recovered nothing is filled "by
bijection": the coverage line reports 70/70 used bytes pinned, 0 completed.

**Result on the chunk: 4,578 unresolved instructions → 0.**
`disassemble` of the same file went from 83,340 `UNKNOWN` lines to 0.

### 7.2 314 dropped bodies, from one accounting bug

With the map solved the output still ended at 57,880 lines with a plausible
tail — and was missing 314 of 1,610 proto bodies. The cause was the
"proto-wide" statement budget: the counter was never suspended when a nested
closure lifted, so main (which owns all 1,609 closures) paid for every one of
their statements out of a single 50,000 allowance. It tripped silently at
statement 50,000 and every later statement was dropped. Nothing dangled, the
file still parsed per-proto, and no check saw it.

Two limits now, both explicit:

* `MAX_STMTS_PER_PROTO` (50,000) — per proto, suspended while a nested proto
  lifts (`enter_proto_frame` / `leave_proto_frame`).
* `MAX_STMTS_PER_CHUNK` (4,000,000) — the real memory guard; when it trips the
  header prints a `-- TRUNCATED` line, so truncation is never silent.

The header also gained a `-- BODIES DROPPED: N of M protos never reached the
emitter` line, because a missing body is the one defect the source cannot show.

**Result: 314 → 2 dropped bodies** (99.88 %), and main's missing calls went
from 505 to 5.

### 7.3 Four passes were quadratic (one of them exponential)

The decompile had never finished; after 7.2 it still ran past 20 minutes. Each
pass was timed (`LUAU_TIMING=1`, `LUAU_TIMING_VERBOSE=1`):

| pass | shape | fix |
|---|---|---|
| `eliminate_dead_stores` | per assignment, scan to the end of the block; `Vec::remove` per drop | name→position index + mark-and-compact |
| `eliminate_dead_key_eq_value_locals` | per local, walk the whole remaining tail twice | per-statement read/write name index + binary search; mark-and-compact instead of `remove` |
| `eliminate_dead_code` phase 3 | `remove(i)` inside a scan loop | one rebuild pass |
| `exits_on_all_paths` | recursed on **every suffix** → 2^n on a block of `if c then break end` | right-to-left suffix table, O(n) |

`exits_on_all_paths` was the worst: a 2,140-statement block of break-guards in
the client chunk made it effectively hang. Every one of these rewrites is
behaviour-preserving, and the corpus outputs stayed **byte-identical**.

**Result: 1 m 9 s** for the full chunk (from unbounded).

### 7.4 Output that does not parse

Four statements reached the emitter with an empty value list and printed as
`x = ` — a syntax error, which cost the whole file: the official Luau parser
rejected everything after the first. They are now emitted as
`x = nil --[[ MISSING RHS ]]` and counted in the header
(`-- MISSING RHS: 4 assignment(s)`), so the file always parses and the damage
is stated rather than hidden. Silent `nil` would be a behaviour change; a
counted one is a documented gap.

**Result: 0 syntax errors** from `luau-analyze` over 72,787 lines.

### 7.5 Tests that had baked in the wrong opcode table

330 hard-coded `const OP_*: u8 = <number>` constants across 28 test files
encoded the drifted numbering, so the suite would have gone on "passing"
against a table that mis-decodes real bytecode. They now derive from
`LuauOpcode::X as u8`, which makes that class of drift impossible.
`canonical_luau_to_internal` also stops at 82 (canonical Luau has 83 opcodes;
83+ are Roblox extensions), and `fresh_overrides_cache` keys on the real
generic-for pair (`FORGPREP_INEXT` / `FORGPREP_NEXT`) instead of the
`Deprecated61` placeholder.

**`cargo test --release --workspace --all-targets`: 1,057 passed, 0 failed,
12 ignored** (the `-p luau-core --lib` subset of this is 959/0/11).
The harness also compared error _locations_ (`path:line`), which differ
between a `.luac` and a `.lua` run by construction; it now compares error
_messages_. Corpus results are unchanged case for case: 27 pass / 21 mismatch /
23 run-fail, byte-identical decompiler output.

### 7.6 What is still open

* ~~**2 protos of 1,610** (616, 617) never reach the emitter.~~ **CLOSED in
  §8.** They were never missing: `NEWCLOSURE`'s D field is a *child-list
  position*, and the two sites at pc 27196 / 27254 carry `P343` / `P344`, which
  resolve to protos 616 / 617. The pcs previously blamed (58771, 58838) carry
  `P616` / `P617`, i.e. positions 616 / 617, which are protos 999 / 1000 — a
  different, equally valid pair of closures. The decompiler was right.
* **4 assignments** still arrive without a value (counted and marked).
* The corpus's remaining 44 cases (per-iteration capture, vararg echo,
  metatable `concat`, numeric-for shadowing, OOP, coroutines, big-module,
  second string file) are unchanged from before this work.

## 8. The umbrella `if` that swallowed whole function bodies

### 8.1 What was wrong

`structure_control_flow` emits an `IfThenElse` for every block with two
successors. When the two arms never reconverge, `find_merge_point` returns
`None`, and `collect_region_blocks(branch, None)` then returns **every block
reachable from the branch** — the rest of the function. That whole body becomes
the `else` arm.

Measured on the 1.8 MB client chunk, proto `?@4836` (117,864 instructions,
parent of 1,021 protos) structured to exactly **one** region:

```
REGIONDUMP ?@4836 len=117864 n=1 :: If(c0)[1 blk|7951 blk]mNone
```

The function starts with a guard clause (`if cond then return end`), so the
fall-through arm is a single terminating block and the "else" arm is everything
else — 7,951 blocks. The ARM lifter (`structure_numeric_for_body`, which knows
loop shapes and a couple of narrow `if` shapes) then flattened the entire
program body, and the flat walk dropped every span it jumped over.

Concretely, at pc 27077 a `JUMP -> 27282` skipped 27079..27281 — the `elseif`
arm holding two `NEWCLOSURE`s and 25 `CALL`s. `LUAU_WALK_COVER=1` reported
`CALLGAP ?@4836 missed=25/9842`.

### 8.2 The fix

A guard clause is not an umbrella. When `merge` is `None` **and** the
fall-through arm terminates (every block in it ends in `RETURN`), emit the
guard alone — `IfThenElse { then_region: <fall-through>, else_region: [],
merge_pc: None }` — and leave the branch side unhandled so the RPO loop
structures it normally. Gated on `LUAU_NO_UMBRELLA` (default on; `=0` disables
it for bisecting).

### 8.3 Measured

| | before | after |
|---|---|---|
| regions for `?@4836` | **1** (`If[1 blk \| 7951 blk]`) | **523** |
| `CALLGAP ?@4836` | `missed=25/9842` | **`missed=3/9842`** |
| chunk-wide missed calls | 25 in one proto | **10 across 6 protos** |
| `BODIES DROPPED` header | `2 of 1610 protos: [616, 617]` | **absent (0 dropped)** |
| call-recovery header | 1 proto, 5 calls short | 1 proto, 5 calls short |
| emitted source | 72,787 lines / 3,651,835 B | 72,243 lines / 3,437,528 B |
| `cargo test --release -p luau-core` | 959 pass | **959 pass, 0 fail** |
| corpus (72 cases, v9) | 28 pass / 21 mismatch / 23 run-fail | **identical verdicts** |

The 12 corpus outputs that differ textually are all the same improvement:

```lua
-- before                              -- after
if cond then                           if cond then
    return a                               return a
else                                   end
    <rest>                             <rest>
end
```

i.e. guard clauses are recovered as guard clauses instead of as `else` bodies —
semantically identical, and closer to the source that produced the bytecode.
Every other corpus output is byte-identical.

Syntax check on the chunk: `luau-compile --binary` fails at the same place
before and after (`Out of upvalue registers ... exceeded limit 200` at
line 8/9, column 2941) — an inherent property of a 71-upvalue, 117k-instruction
function, not a regression.

### 8.4 What is still open

Three `CALL`s in `?@4836` (pcs 27748, 112211, 112344) are still skipped, and
they are all the same shape: an `elseif` arm whose entry point is the target of
a *different* link of the chain, sitting inside a span some other region already
claims. The flat walk reaches an unconditional `JUMP` that steps over the arm
(`27735: JUMP -> 27750` skipping 27736..27749) and nobody owns the skipped
span. The next fix belongs in `structure_numeric_for_body`: it needs a general,
CFG-driven `if`/`elseif`/`else` shape instead of the current
`spans_loop && tiles` special case, so arm-lifted spans get the same structure
the top level now gets.

## 9. Patch hygiene: a fix that only compiled for the lib target

### 9.1 The report

Applying this patch to a clean fork failed to compile:

```
error[E0433]: cannot find type `LuauOpcode` in this scope
  --> crates/luau-core/examples/decompile_demo.rs:28:22
   |
28 | const OP_LOADN: u8 = LuauOpcode::LoadN as u8;
```

### 9.2 Cause

An earlier fix replaced hard-coded opcode bytes with named constants —
`const OP_LOADN: u8 = 4;` became `const OP_LOADN: u8 = LuauOpcode::LoadN as u8;`
— in every file that declared them, `examples/decompile_demo.rs` included. The
rename landed but the `use` that makes `LuauOpcode` resolvable did not, because
examples build as a **separate crate**: `crate::` paths reach nothing there, and
the type has to come in through `luau_core::…`.

It survived every verification run because the command used to verify was

```sh
cargo build  --release -p luau-core -p luau-cli      # lib + binary only
cargo test   --release -p luau-core --lib            # lib tests only
```

Neither compiles `crates/*/examples/`, `crates/*/tests/` or benches. The
defect was not subtle; it was simply never looked at. `--lib` reads as "just
the library" and quietly means "and nothing else that ships".

### 9.3 Fix

```rust
use luau_core::parser::opcodes::LuauOpcode;
```

plus this note at the declaration site, since the import is the non-obvious part:

```rust
// The explicit import is required: examples build as a separate crate, so
// nothing here is reachable through `crate::`.
```

While there, an earlier edit of mine to `structure_block_subset` had left a
shadowed pair of `collect_region_blocks` BFS calls whose results were never
read (`unused variable: then_blocks / else_blocks`); removed. Both defects were
found by warming up the warnings, not by reading the diff.

### 9.4 Verification now, and going forward

The patch is verified by applying it to a **fresh clone** and building there,
not by building the working tree:

```sh
git clone --depth 1 https://github.com/PumbaaDev/luau-decompiler.git /tmp/applytest
cd /tmp/applytest
git apply --check -p1 /home/user/luau-decompiler-fixes.patch   # applies clean
git apply -p1 /home/user/luau-decompiler-fixes.patch
cargo build --release --workspace --all-targets                # every target
cargo test  --release --workspace --all-targets                # 1,057 / 0 / 12
cargo run   --release -p luau-core --example decompile_demo    # the demo runs
```

The patch is now generated with `a/`…`b/` prefixes, so `git apply -p1` and
`patch -p1` both work; the previous absolute-path form needed `-p3` and failed
with a bare `git apply`.

**Process change:** `bootstrap.sh` now builds `--workspace --all-targets`. Any
future patch is compiled in the shape a user receives it, examples and
integration tests included.

Re-running the decompiler on the 1.8 MB chunk after this change produces a
**byte-identical** 3,437,528 B output, so none of it perturbs the results in
§8.

## 10. A second, larger client chunk: `SUBRK` operand order and unreachable protos

The hard target was replaced with a newer build of the same script —
**3,536 protos, 2.37 MB, main proto #3535 at 13,304 instructions** (the previous
one was 1,610 protos / 4,151 instructions).

First run on it was a catastrophe: **1,836 of 3,536 protos dropped**, 18 opcode
bytes unmapped, 151 unresolved instructions, 526 KB of output. Two defects, one
fatal and one merely lossy.

### 10.1 `SUBRK`/`DIVRK` are the reversed-operand pair, and the opkey gate did not know

The fatal one was a **false negative in opcode-key recovery**, and it is worth
stating plainly because the gate's design is what made it fatal rather than
degraded:

`parser::opkey::recover` brute-forces all 128 odd multipliers and accepts a
candidate only when *every* proto chains exactly with zero structural
offences (`MAX_OFFENDERS = 0`). Its constant-index check lumped `SUBRK` and
`DIVRK` in with `ADDK`/`SUBK`/`MULK`/… and read the index from **C**.

They are not in that family. `Bytecode.h`:

```
// SUBRK, DIVRK: compute arithmetic operation between the constant and a source register
// A: target register
// B: constant table index (0..255); must refer to a number
// C: source register
```

vs.

```
// ADDK, SUBK, MULK, DIVK, MODK, POWK: ... between the source register and a constant
// B: source register
// C: constant table index (0..255); must refer to a number
```

So on the 7 `SUBRK`s in protos 3402/3403 the gate read a live **source
register** (values 6, 8, 10, 11, 13, 15) as a constant index into a proto with
1 and 3 constants. Seven offences. `MAX_OFFENDERS = 0`. The **only** multiplier
that chained all 3,536 protos (`mult=203`, encode_key 227) was rejected, and
decoding fell through to the detector/bijection path, which is what dropped
1,836 protos.

```
opkey: best mult=203 exact=3536/3536 bad_jumps=0 bad_consts=7   <- rejected
opkey: best mult=203 exact=3536/3536 bad_jumps=0 bad_consts=0   <- after the fix
opkey: recovered multiplicative opcode key 227 (multiplier 203); 3536 / 3536 protos chain exactly
```

`FASTCALL2K` had the same mistake in the same match arm — its constant lives in
**AUX**, not C:

```
// FASTCALL2K: ... B: source argument register / C: jump offset to following CALL / AUX: constant index
```

Both are fixed. The lesson is not "loosen the gate": the gate was measuring the
wrong operand, and a correct gate is what makes the key recovery a decision
rather than a heuristic. Note also that the **lifter was already correct** here
(`R(A) = K(B) - R(C)`), so this was purely a scoring defect — the decompiler
knew how to render `SUBRK` and still refused to decode the chunk containing one.

### 10.2 Eight protos nothing refers to

With the key fixed, 8 of 3,536 protos still never reached the emitter:
`[212, 213, 228, 229, 231, 232, 234, 235]`.

These are genuinely **unreachable**: an independent parse of the container
found no `NEWCLOSURE` child slot and no `DUPCLOSURE` closure constant naming any
of them, and they are the ONLY 8 protos in the chunk in that state. A proto no
path from `main` can construct is never lifted, so it was silently absent from
the output — the emitted source stopped describing the chunk it came from.

`lib.rs` now sweeps for protos missing from `proto_coverage()` after the main
lift and emits each one in a marked trailing section:

```lua
-- ===== ORPHAN PROTOS: 8 unreachable function(s), kept so nothing is lost =====

-- proto #212: unreachable in this chunk (no NEWCLOSURE child slot and no
-- DUPCLOSURE constant refers to it). Emitted so no body is lost; never called.
local function anonymous_212()
    ...
end
```

Wrapping each in a `local function` is what keeps this behaviour-preserving: a
function body does not run when it is defined, and the protos are unreachable by
construction, so nothing can call them either. `BODIES DROPPED` is now absent
from the header — **0 of 3,536**.

### 10.4 What is still open — and it is now the only thing between us and runnability

`luau-compile --binary` rejects the recovered source at **line 7**:

```
CompileError: Out of registers when trying to allocate 858 registers: exceeded limit 255
```

Line 7 is `free_var_decls`' single hoisted declaration:

```lua
local Angles237, AssemblyLinearVelocity, ..., v53   -- 858 names
```

Those names are **"assigned somewhere but never bound"** — 849 of the 858 are
written somewhere in the file. They are *not* real upvalues: this chunk's main
proto has **0 upvalues** and `stack=173`. They are locals whose declaration the
lifter lost, which `free_var_decls` then hoists to module scope as a mitigation.

The old chunk has exactly the same defect (493 such names) and fails at the
upvalue limit instead (`exceeded limit 200`). So both chunks are blocked on one
pre-existing issue, and it is the reason "execution-verified equivalence" is
still unmet: the recovered source cannot be compiled, so it cannot be run
against the original.

Three candidate directions, in ascending order of risk:

1. **Declare only on collision.** Keep a module-level local only for names that
   would shadow a real global (`script`, `game`, `task`, …; `is_known_global`
   already knows the list) and let the rest be implicit globals. Inside one
   Roblox script each script has its own environment, so a file-local name and a
   script-global are indistinguishable — but this changes the pass's deliberate
   behaviour and needs the corpus run to back it.
2. **Find the lost declaration.** These are `WriteKind::FirstDecl` cases that
   never emitted a `local`. Fixing the root cause removes the hoist entirely and
   is the only version that is right everywhere, not just for this chunk.
3. **Cap and report.** Declare at most N and leave the rest global with a header
   note. Cheap, honest, and leaves the defect visible.

(2) is the correct fix and is where the next rotation should start; (1) is the
cheap experiment that tells us how much of the 858 is genuinely collision-risk.

## §11 — The 255/200 register ceiling: three wrong placements, measured

The client chunk decoded every opcode and emitted every body, then failed to
**compile**. Three separate causes, each with a different owner.

### 11.1 Chunk-top hoist → 858 registers at line 7 (fixed: `declare_scoped`)

`free_var_decls::declare_free_vars` put every unbound-assigned name into ONE
chunk-top `local`. The chunk's main proto declares `stack=173`, and Luau allows
200 locals per function, so a single 858-name statement could never compile.

Placement, not admission, was the bug. An assignment to a name the function
never declares is, in the original source, a `local` at the top of **that**
function — which is where the lifter's register tracker already believed it had
put one. `declare_scoped` walks the tree and declares each admitted name in the
innermost function that assigns it, recursing into closures with the inherited
scope. The admission rules are unchanged: the pass receives the old chunk-top
set as `admitted` and may only declare names from it, and anything the walker
does not reach stays at chunk top, so a file that used to work cannot regress
through this change.

Measured: 858 → 0 chunk-top names on the client chunk (`local v11, v53`
remains, both genuinely top-level).

### 11.2 Materialised closures → 1,403 top-level `local function` (fixed: `sink_single_use_closures`)

The dominant shape was

    local function BindImpact(self, arg2, arg3) ... end
    ...
    local VFXService = { BindImpact = BindImpact, ... }

1,403 of these sat at the top level of a 173-register proto. Each one is read
exactly once, in the block that creates it, so no name was ever needed:
sinking it into the use site restores the source shape
(`{ BindImpact = function(self) ... end }`) and gives the register back.

Safety envelope: exactly one read in the whole function, that read in a DIRECT
statement of the same block (never a loop body, so one closure cannot become
one-per-iteration), the read after the declaration, and no `local` in between
binding a name the closure body reads. Measured: 1,403 → 70.

### 11.3 Register reuse materialised as new locals (fixed: `classify_write_ex`, `classify_write_nonfn`)

`WriteKind::Shadow` fires whenever `ctx.reg_name`'s hint differs from the
recorded name, and that hint is PC-scoped — the same register is renamed on
every pass. Shadow is not optional (see below), but it costs a register per
lifetime. `classify_write_ex` tells the classifier what value is being stored
and reuses the existing binding for everything except closures; the opcode
handlers that cannot produce a function value (GETGLOBAL / GETIMPORT /
GETTABLEKS / NEWTABLE / CALL) use `classify_write_nonfn`.

Why functions keep the shadow: collapsing two closure writes onto one name
(`F = f1; F = f2`) makes the first a plain overwrite, and dead-store
elimination deletes it — together with the proto body it held. Measured during
this work: 3,568 → 200 `function` keywords, i.e. 3,336 protos dropped. The
compile error moved from line 7 to line 15033 on that change, which is how the
regression was caught: a closer error is not progress if bodies vanished.

### 11.4 Copy chains (fixed: `propagate_single_use_copies`, narrowly)

A `MOVE` between two registers is materialised as a fresh local, so a value
shuffled along a register chain arrives as

    local Assets52 = Assets51
    local Assets53 = Assets52
    ...

`propagate_single_use_copies` inlines such a copy into its single reader when
nothing rebinds the source in between. It is restricted to a RHS that is
exactly a `Name`. Generalising it to any pure initialiser collapsed far more
register pressure but reordered value construction against the surrounding
statements and cost 10 of the 20 corpus cases that round-trip (20 → 10 PASS);
it was reverted. Register pressure belongs at the write site, where the
bytecode has already decided the lifetimes.

### 11.5 Result

    protos                              3,536 / 3,536, no drops
    `function` keywords                 3,568

    luau-compile --binary               exit 0 (2,634,637 bytes)
    luau-analyze                        no syntax errors, no unknown globals
    cargo test --workspace --all-targets 1057 passed / 0 failed

## §12 — Round 2: defects from the dev bug report

Measured with `work/real/detect.py`, which implements the report's own detection
recipes so every claim below is reproducible:

    python3 work/real/detect.py ClientRenderer_new.decompiled.lua

### 12.1 Dropped `#` (report bug #2) — FIXED

Symptom: `for i = 1, tbl436 do` for `for i = 1, #tbl436 do`, "invalid 'for'
limit (number expected, got table)".

Cause: `ctx.unary.length` was `Passthrough`, so the `LENGTH` handler copied its
operand and dropped the operator. That default exists because a *misdetected*
opcode map makes `LENGTH` look like `#` where it is not; but it is per-dialect,
and this chunk genuinely compiles `#x` to `LENGTH`. The chunk has 88 `LENGTH`
words / 90 lift sites and only 42 `#` in the output.

Fix: `DecompileContext::infer_length_semantics` measures the chunk instead of
assuming. A repurposed `LENGTH` writes its operand value out (a field, a table
slot, a call argument); a real `#` feeds arithmetic or a numeric-for bound. The
scan counts both and upgrades only on a lopsided ratio (>=4 arithmetic
consumers, numeric-operand sites <= 1/4 of them). This chunk reads 48 vs 2.

Result: 42 -> 139 `#` in the output. The reported function now lifts as

    for i = 1, #arg1 do
        local sub = string.sub(arg1, i, i)
        sub = #arg1 - i + 1
        if #arg1 % 2 == 1 then

No `#<numeric literal>` is produced (checked; the only `#` followed by a digit
is inside the string constants `"Speedblitz#1"`).

### 12.2 Locals shadowing library constructors (report bug #4) — PARTIAL

`is_stdlib_shadow_name` listed the stdlib globals and `game`/`workspace`/`script`
but no Roblox datatype, so a field-derived name could declare
`local CFrame = RootPart.CFrame` and make the next `CFrame.new(...)` call nil.
The denylist now covers the constructor-bearing datatypes (CFrame, Vector3/2,
UDim2, Color3, ColorSequence, NumberSequence, Rect, Ray, TweenInfo, BrickColor,
Instance, Enum, Random, ...). `Instance` no longer appears as a local.

Still emitted: `local CFrame = ...` and `local Color3 = self.Color`, e.g.

    local Color3 = self.Color
    if not self.Color then
        Color3 = Color3.fromRGB      -- reads nil.fromRGB
        Color3 = Color3(105, 195, 0xFF)
    end

These two do not come through `synthesize_name`'s guarded `Named` arm, so the
denylist does not reach them. Open.

### 12.3 Undeclared SSA names (report bug #1) — SUBSTANTIALLY FIXED, not complete

Reported: 790 names / 3,202 sites. Measured on the shipped file with the
report's own recipe: **689 names / 7,444 sites**.

Cause, proved on `tbl5`: the parent's register holds a table literal and a
closure captures it (`NEWCLOSURE R81 P13` / `CAPTURE val 79` at pc 762, where
R79 is the `DUPTABLE` at pc 697). The `CAPTURE` handler names the upvalue by
*inferring* from whatever the value tracker happens to hold at that moment —
field name, method name, string argument, else `ctx.reg_name` — and `reg_name`
mints `tbl5` for a register the parent actually bound as `tbl`. Nothing ever
declares `tbl5`, so every read in the child is a nil global read.

Fix (B0.132b): the upvalue IS the parent's local. Before any inference, the
`LCL_VAL` / `LCL_REF` capture path now takes the analyzer's `current_name` for
the captured register — that is the binding the parent actually emitted, not a
guess — and falls back to the old inference only when there is no live binding.

Result: 7,444 -> **635 sites** (139 names). No bodies lost (3,568 functions
before and after), corpus unchanged, 1057/0 tests.

Remaining, by base name: `e` 418 sites, `Parent*` 112, `RaycastParams` 26,
`script_*` 15, `upval_*` 12, `lib` 10, then a long tail. `e` is the largest and
looks like a single captured-variable shape repeating.

### 12.4 Not yet addressed

### 12.5 Dropped method call / register reuse (report bugs #3 and #7) — FIXED

`§11.3`'s `classify_write_nonfn` (reuse one name per register instead of
shadowing) was **wrong**, and it caused this:

    value2 = value2:ToObjectSpace(value)   -- deleted as a dead store
    value2 = CFrame.new(CameraOffset)
    value2 = value2:Lerp(value2 - vec, k)

Three different lifetimes were collapsed onto one name, so the `SUB` that read
the second value was folded forward past the third write and the
`:ToObjectSpace` call vanished — the report's "Unable to cast Vector3 to
CoordinateFrame, every frame", with the orphaned `CFrame65`/`CFrame66` locals
as its fingerprint. Same mechanism is bug #7 (a `GetAll` builder reassigned to
a `WaitForChild` result).

Reusing a name is only sound while the old value is DEAD at the new write, and
the lifter has no liveness information. The collapse is disabled; register
pressure is carried by scoped declarations, closure sinking and copy
propagation, which turn out to be sufficient — the chunk still compiles.

Repro (before): `work/mini3/t4.luau` loses `:ToObjectSpace` at every -O level.
After: `Root.CFrame:ToObjectSpace(Head.CFrame) - Vector3.new(...)` is emitted.
Corpus went 20 -> **28 PASS** (full baseline parity).

### 12.6 Numbers rewritten as strings (report bugs #6, #8b, #9) — MOSTLY FIXED

B0.124 ("resolve Number arguments that are really constant indices") rewrote
EVERY numeric argument of GetService/WaitForChild/FindFirstChild*/IsA/
GetAttribute/SetAttribute into `constants[n]` as a string. Any genuinely
numeric argument was therefore replaced by whatever string sat at that index:

    WaitForChild("Bars", 15)  ->  WaitForChild("Bars", "UserService")   (#8b)
    SetAttribute("Id", k3)    ->  SetAttribute("Id", "Instance")        (#6)

The timeout rewrite is gone (measured 9 -> 0). The pass now touches argument 0
only (the one position that can be a name) and refuses to substitute a known
method name.

Still open: 3 `WaitForChild("FindFirstChildOfClass")` sites. The bytecode shows
`MOVE R115 R111` feeding the call, where R111 holds `"Icon"`/`"IconNew"` from
the ternary on the preceding line, so the argument register is being read as
the method-name string instead of its value. Distinct from the above.

### 12.7 Backwards constant-index scan: `GETUPVAL R4 U0` -> `constants[0]` — FIXED

Two rules rewrote call arguments for `GetService`/`WaitForChild`/`FindFirstChild*`/
`IsA`/`GetAttribute`/`SetAttribute`.

Rule A (`B0.124`) resolved *any* numeric argument as `constants[n]`. Rule B scanned up
to six instructions backwards and, on the first one whose `A` field matched the argument
register, read its `D` field as a constant index. For

    GETUPVAL R4 U0          -- D = 0  (upvalue index)
    MOVE     R115 R111      -- D = 111 (register number)

that produced `constants[0]` = `"Instance"` and `constants[111]` =
`"FindFirstChildOfClass"`, i.e. the dev report's

    SetAttribute("Id", k3)   ->  SetAttribute("Id", "Instance")          (#6)
    WaitForChild(v)          ->  WaitForChild("FindFirstChildOfClass")    (#9)
    WaitForChild("Bars", 15) ->  WaitForChild("Bars", "UserService")      (#8b)

Rule B now accepts only a genuine `LoadK`, and rule A only touches argument 0 (the one
position that can be a name) and refuses to substitute a known method name.
Measured: WFC_BAD_TIMEOUT 9 -> 0, METHOD_AS_CHILD 3 -> 0.

### 12.8 Undeclared `.Parent` temps — FIXED for 85 sites

`if character and character.Parent then` compiles to

    GETUPVAL  R0 U0 ; JUMPIFNOT R0 ; GETUPVAL R0 U0 ; GETTABLEKS R0 R0."Parent" ; JUMPIFNOT R0

When the value-selection path lifts the second test it can materialise the `GETTABLEKS`
result as a register temp whose defining statement is then dropped:

    if Character ~= nil and Parent173 ~= nil then   -- Parent173 is a nil global

`post_passes::restore_dropped_parent_temps` rewrites the flattened `and` chain using the
operand immediately to the left as the subject (that is exactly the table the bytecode
read `.Parent` from). Only a `Parent<digits>` temp proven undeclared in scope, and only
when both neighbours are `~= nil` tests, are touched. 85 recoveries on this chunk.

### 12.9 Orphan protos and library-global shadows — FIXED

* The 8 detached protos (of 3,536) were emitted through `decompile_proto(depth=1)`, so
  `declare_free_vars` never ran and every free read (`script_2`, `lib`, `upval_N`) became
  a nil global. New `decompile_orphan_proto` runs it in orphan mode: nothing to capture,
  nothing to shadow, so every free name is declared.
* `unique_name` appends a counter, so a harmless prefix can still collide with a library
  global — `Color` + 3 = `Color3`. `is_stdlib_shadow_name` screened the prefix only; it is
  now re-checked on the final spelling. LIB_SHADOWS 2 -> 0.
